# Service objectives

Initial 30-day availability objective: 99.9% of completed API requests return below 500. Health and scrape traffic are excluded. Aborted requests, ingress failures and a fully unreachable backend need a separate external synthetic probe; HTTP counters alone cannot detect them.

Targets: GET p95 300ms, training answer p95 350ms, training create p95 800ms, Mongo p95 100ms, Redis p95 10ms. Frontend targets remain LCP p75 2.5s, INP p75 200ms and CLS p75 0.10, measured through the existing frontend telemetry. Targets are objectives, not measured results.

Set a dedicated `METRICS_TOKEN` and scrape `/metrics` with its bearer token. Scrape every backend instance under job `meow-backend`; retain instance labels. Import `slo-rules.yml` into Prometheus and `dashboard.json` into Grafana, then configure alert routing. No messages or alerts are sent by local verification. Keep staging and production in separate monitoring tenants or add environment selectors before combining their metrics.

Dashboard queries: `meow:get_latency:p95`, `meow:mongo_latency:p95`, request rates grouped by route, 5xx rates, `meow_process_resident_memory_bytes`, `meow_nodejs_eventloop_lag_p99_seconds`, and `meow_dependency_errors_total`. Use histogram_quantile over dependency buckets for AI/storage. Request labels contain route templates, never user IDs, question IDs or prompts.

Follow the multiwindow burn-rate method from [Google SRE](https://sre.google/workbook/alerting-on-slos/). For low traffic, require synthetic probes and inspect request volume before paging solely on a ratio.

Staging load order is C1 → C5 → C10 → C25 → C50 → C100. Stop at the first latency/error regression. The manually invoked staging workflow verifies the isolated database and `/health` environment before creating temporary learners; cleanup always runs. Keep production probes at their existing small limits. Local fixtures and CI Redis recovery tests do not establish Azure/Atlas capacity.

Staging templates: `prometheus.staging.example.yml`, `backend-instances.staging.example.yml`, `blackbox.example.yml`, `alertmanager.staging.example.yml` and `otel-collector.staging.example.yml`. Replace `.invalid` targets, mount secrets as files, and restrict collector ingress to backend instances. Set `OTEL_ENABLED=true`, `OTEL_EXPORTER_OTLP_ENDPOINT` to the collector HTTP base endpoint, `OTEL_SERVICE_NAME=meow.backend.staging`, `DEPLOYMENT_ENVIRONMENT=staging`, and a dedicated backend `METRICS_TOKEN`. Per-instance scraping requires direct instance discovery or an agent on every instance; an Azure load-balanced hostname alone cannot provide reliable per-instance series. Verify OTLP receipt, authenticated scrapes, `meow:training_create_stage:p95` and the imported dashboard. The HTTP probe checks 200 plus `ok:true` on both `/live` and `/health`, including external DNS/TLS/ingress reachability. Run it outside Azure. `MeowExternalProbeMissing` also checks the exporter itself.

Validate with `promtool check config prometheus.staging.example.yml` after mounting referenced files, `promtool check rules slo-rules.yml`, `promtool test rules slo-rules.test.yml`, and `amtool check-config alertmanager.staging.example.yml` after mounting the receiver file. Use a controlled staging-only test alert and record received/resolved timestamps before accepting delivery. No template provides evidence of activation or sends a notification by itself. Configuration follows the [Prometheus HTTP/scrape configuration](https://prometheus.io/docs/prometheus/latest/configuration/configuration/) and [Blackbox exporter configuration](https://github.com/prometheus/blackbox_exporter/blob/master/CONFIGURATION.md).

Local creation stage diagnostics are included in the cold/warm load report. They are overlapping wall-clock durations (history/state run in parallel) and must not be summed as a sequential trace. Histogram p95 estimates need adequate traffic volume; the short local report provides count and mean for finding bottlenecks.
