**Corrections and additional findings that change the order**

1. **Normalization currently has a reproducible migration defect.** `backend/scripts/normalize-question-keys.js:12` does not project `questionType`, `word`, `meanings`, or `letter`, although `deriveModeKey()` uses them. A local invocation of the actual normalizer with a study-mode vocabulary record returned `studyMode`; the same record reduced to the backfill projection returned `concept`. The projection also omits existing `modeKey`, so the equality check cannot recognize already-correct rows. The script reports candidate changes, not actual modifications, and treats explicit null values as missing in its concurrency predicate. Do not run this backfill unchanged.
2. **Not every ingestion path writes normalized keys.** `backend/controllers/imageQuestionController.js:172` and `backend/routes/massUploadImages.js:118` insert directly. Those paths also bypass the question service's cache invalidation. Backfilling once will not keep the data normalized while these writers remain active.
3. **Socket.IO already has a scaling foundation.** `backend/battle/battleSocket.js:81` installs the MongoDB adapter and enables connection recovery. But workers call process-local realtime getters: `emitMatchFound()` and notification emitters return without publishing if the server reference is absent. Merely moving imports to `worker.js` can silently lose user events. A separate Mongo emitter is supported by [Socket.IO's official adapter documentation](https://socket.io/docs/v4/mongo-adapter/); an outbox is needed where recovery across the database-commit/publish gap matters. The adapter itself is not a durable business-job queue.
4. **Mongo startup can bypass a failed index pass on retry.** `connectMongoDB()` assigns module-level `db` before awaiting indexes. After an index rejection, the next invocation returns `db` immediately. The API retry loop can therefore proceed without a successful complete index pass. Fix connection state handling while extracting migrations.
5. **Deployment is not coupled to the security workflow.** `.github/workflows/main_quizguru-backend.yml:44` deploys after its own build/test job. Removing `continue-on-error` in another workflow does not itself prevent this production deployment. Preserve its backend-local `npm ci --workspaces=false` and lockfile contract while connecting the gates.
6. **Rate limiting also needs attention before multiple replicas.** The limiter definitions have no shared store. Their common key generator accepts `req.cookies.userId`, an untrusted client value, before falling back to IP. Use authenticated identity only after authentication, otherwise normalized IP; add a shared store or centrally enforced limit. The default store is process-local, per the [express-rate-limit store documentation](https://express-rate-limit.mintlify.app/reference/stores).
7. **Frontend recommendations are partly already implemented.** Geometry/Konva consumers use dynamic imports; `HomeClient.tsx` uses `GradientWavesLazy` for OGL. Monaco remains statically imported by the notes editor, but its impact on other routes needs bundle evidence. Providers are already separated by route group. Direct `NEXT_PUBLIC_API_URL` reads remain in notes components, and `frontend/next.config.ts:4` retains the production Azure fallback.
8. **Lighthouse coverage is narrower than the review suggests.** `frontend/lighthouserc.cjs` enforces the stated 0.90 / 2500 ms / 0.1 thresholds, using desktop runs on `/login` and `/mathematics` while blocking backend API requests. These are useful gates, but they do not measure mobile quiz interaction, live API latency, or concurrent battles.

**Deployment and recovery requirements**

- Keep API and worker code in the same backend package initially, with commands such as `start:api`, `start:worker`, and `db:migrate`; do not require a repository-wide `src/modules` relocation.
- Retain the existing Mongo-backed scheduling/claiming mechanisms where they meet the required lease/retry semantics. Use a durable Mongo job collection for the first extraction queue if appropriate; adopt another broker only after its delivery and operational benefits are established. Keep CPU-heavy extraction in a separate worker role from latency-sensitive battle maintenance.
- Migrate indexes before deploying code that relies on them. Use additive migrations and verify unique-index prerequisites. A migration lock needs ownership, recovery and safe completion semantics; a recorded version alone is insufficient if required indexes can drift.
- Deploy the worker with role controls, verify readiness/heartbeats, then disable embedded API workers. Make overlap safe through durable claims and idempotent effects. Keep realtime delivery live until workers have drained during shutdown.
- Preserve disconnect/reconnect/forfeit rules, exactly-once database settlement and reward claims, and XP/ELO separation. External push delivery cannot be assumed exactly once; retain deduplication and accurate FCM Accepted terminology.
- Verify replica-set support, Socket.IO transport settings and ingress routing. If HTTP long-polling is retained, sticky sessions remain required with the Mongo adapter. See [Socket.IO's deployment guidance](https://socket.io/docs/v4/mongo-adapter/).
- Keep legacy display fields and storage references until the new reads have passed parity and restore checks. Roll back readers/process roles against additive schemas; avoid coupling rollback to dropping indexes or deleting old objects.
- Asynchronous tutor extraction must have an explicit client rollout and recovery policy. Decide whether older clients temporarily retain a bounded compatibility path or require a coordinated release before removing the synchronous contract.
