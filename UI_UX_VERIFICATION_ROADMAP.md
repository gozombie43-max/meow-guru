# UI/UX audit verification and implementation roadmap

Verified against local `main`, commit `90088ac746bc4c30c7e21f24320e9736184870f4`. The worktree was clean before this review. This document is the only intended repository change; application implementation is not part of this task.

**Assessment.** The audit identifies useful work, especially setup error handling, control overrides, selectable study content, navigation state, and inconsistent modal behavior. Several touch-size claims are inaccurate because they ignore the shared CSS cascade. The proposed new color foundation also duplicates mappings that already exist. Prioritize demonstrated defects, then consolidate incrementally. The numerical 7.9/10 rating and projected 9/10 outcome are subjective, not measured acceptance criteria.

**Verification boundary.** Reviewed the cited source, component markup, theme mappings, modal behavior, browser configuration, CI configuration, and relevant tests. Ran selected unit/component tests and Chrome CSS fixtures. Fixtures load repository styles with representative markup; they are useful for cascade and control geometry, but do not prove complete route layout, interaction, or content-dependent behavior. No full application route matrix, physical-device review, production build, full test suite, or remote CI run was performed.

**Additional keyboard issue found.** `TrainingFilterPicker.tsx:91–103` installs its Enter handler with only `[open]` as an effect dependency. The handler closes over the draft selection from opening; radio changes update `draft` without renewing that handler. Enter can therefore submit an older selection, unlike clicking Done. This is a source-level finding to reproduce and fix alongside the picker accessibility work.

**Proposed implementation sequence**

Treat confirmed usability defects as the first delivery priority. The audit's P0 label is not evidence of an outage; use separate severity and delivery order.

| Phase | Scope and deliverable | Acceptance gate |
| --- | --- | --- |
| 1. Repair interaction fundamentals | Fix setup title collision and error ownership; consolidate immediate loading feedback; restore study-text selection; fix measured undersized setup/exam/quiz-header/language/rail targets. Review the existing interface test contract and add representative controls to its fixtures. | Each affected target meets the project 44px contract; 320px header fits without clipped/overlapping controls; capability/dashboard retries recover independently; local error dismiss works; one session request per activation; readable text remains selectable. |
| 2. Make shared controls authoritative | Remove Play button anatomy overrides first. Add shared form-control sizing and a compact typography/spacing/radius scale using the existing theme foundation. Map remaining fundamental literals where useful; retain semantic scoring/selection colors. Continue through SubjectHub, AI, Battle, Resources, and Admin in small reviewed slices. | Actual computed controls match the shared contract in both themes; labels wrap; selected/correct/incorrect/disabled/focus states remain legible; no new horizontal page overflow. |
| 3. Standardize modal behavior | Build shared modal behavior around the existing native-dialog and navigation patterns, with Dialog, Sheet, and confirmation presentations as needed. Begin with resource upload, AI preview, and training picker; reproduce/fix picker Enter behavior. Then migrate Settings/Admin/Battle and remaining quiz overlays incrementally. | Keyboard focus enters and stays inside; Escape and app/browser Back dismiss only the top layer; opener focus restores; background is inert; nested scroll locks restore correctly; busy confirmations obey their dismissal policy; safe areas and reduced motion work. Verify WebView blur separately. |
| 4. Improve Play navigation | Use canonical `/play?view=mission|mock|review|insights` values with `/play` as default practice; map `insights` to the existing Analytics label unless copy changes are approved. Preserve unrelated query values and the selected exam. Present local navigation with lower visual emphasis. | Direct links, reload, Back/Forward, invalid values, and exam switching behave consistently. All five capabilities remain reachable; no scroll or duplicate-fetch regression. |
| 5. Improve shell and desktop reflow | Verify SubjectHub at short heights/zoom, then add graceful reflow. Review desktop scrollbar visibility. Consolidate shell visibility policy and remove unreachable AI active handling while preserving fullscreen behavior. Consider layout-group changes only if the simpler policy cannot express ownership cleanly. | Topic/search controls remain reachable at 1366×768, 1280×720, and real 200% browser zoom. Existing fullscreen routes retain correct Back behavior and bottom clearance. |
| 6. Establish regression gates | Add representative route browser checks, screenshots, keyboard/modal checks, target measurements, and narrowly scoped static checks. Wire the reviewed interface check into CI. Capture baselines after the approved behavior is implemented. | Target/overflow checks fail on intentional regressions; functional tests and relevant typecheck/lint/build pass; CI invokes the checks. Record exactly which routes, states, and devices were exercised. |

Phase 6 coverage should grow with every earlier phase; do not postpone verification until consolidation is complete. Each phase is a separate reviewable implementation slice, and should proceed only after the relevant acceptance checks pass or an explicit limitation is recorded.

**Required browser matrix for implementation**

- Viewports: 320×568, 390×844, 768×1024, 1366×768, 1440×900; add 1280×720 for SubjectHub. Exercise light/dark themes.
- Content/states: Bengali and long labels, long formulas/questions, submitted correct/incorrect answers, empty/loading/error/retry states, and nested overlays.
- Inputs: keyboard-only navigation, coarse pointer, actual 200% browser zoom, and reduced motion. Device pixel ratio is not a substitute for zoom.
- Representative journeys: Home → subject → quiz; Play → setup → session → results/review; Assistant attachment preview; Resources upload chooser; Settings; Battle exit; Admin editing/confirmation.
- Physical Safari/PWA and Android WebView checks remain necessary for selection, safe areas, keyboard/composer behavior, native-dialog backdrop effects, and device Back.

Static searches can flag suspicious values, but cannot reliably determine computed hitbox geometry, semantic text roles, active CSS overrides, or zoom clipping. Use browser measurements for those gates; permit documented exceptions for decorative controls and backdrop targets rather than failing every small pixel literal.

**Preservation boundaries.** Keep the quiz card/options/solution structure and scoring colors, server-authoritative training/session rules, question-derived filters, cursor pagination, API contracts, and existing AI tutor payload/history unchanged during this UI work. This plan does not include a redesign, dependency upgrade, deployment, or database change.

**Recommended first implementation slice:** Phase 1, together with the regression checks needed to prove it. Retain the current fullscreen Assistant and all Play destinations; larger information-architecture choices can follow verified interaction repairs.
